# Stage 2.2.1 — Development Toolchain Planning

## Status

**Overall:** Completed — Revised for Full-Stack Architecture

## Objective

Define the development-toolchain foundation for the JavaScript Notebook rebuild before installing application dependencies.

The JavaScript Notebook is a full-stack application consisting of:

* Frontend presentation and interaction
* Backend application and runtime services
* Shared contracts and types
* Supporting infrastructure

The project must remain a single Git repository while maintaining clear architectural boundaries between these areas.

---

# 2.2.1.1 — Architectural Toolchain Scope

The development toolchain must support the complete application rather than treating the project as a frontend-only application.

The planned repository structure is:

```text
JavaScript Notepad/
│
├── frontend/
│   └── Browser-based presentation layer
│
├── backend/
│   └── Server-side application and runtime services
│
├── shared/
│   └── Shared types, schemas and contracts
│
├── docs/
│   └── Project documentation
│
├── package.json
├── .gitignore
├── .gitattributes
└── .env.example
```

This structure is a planning target.

The directories must be introduced through the appropriate repository/source-architecture stages rather than created prematurely during toolchain installation.

---

# 2.2.1.3 — Backend Toolchain

The backend is a first-class part of the project.

It will provide server-side capabilities required by the notebook architecture.

Potential backend responsibilities include:

* Application APIs
* JavaScript execution services
* Execution state management
* Execution instrumentation
* AST analysis services
* Program analysis services
* Data-flow analysis
* Runtime information processing
* Persistence
* Notebook storage
* Export services
* File handling
* Infrastructure integration

The exact implementation of these responsibilities is intentionally deferred until the corresponding architecture has been designed.

## Backend Language

TypeScript is selected as the primary implementation language for the backend as well as the frontend.

This provides a consistent language across the full-stack project while allowing independent architectural boundaries.

## Backend Runtime

Node.js is selected as the development/runtime environment.

The specific backend framework and server architecture are deferred until the backend architecture stage.

---

# 2.2.1.4 — Shared Layer

A shared layer is planned to prevent unnecessary duplication between frontend and backend contracts.

Potential shared responsibilities include:

* Domain types
* API request/response contracts
* Validation schemas
* Notebook data structures
* Cell models
* Execution result contracts
* Analysis result contracts
* Error contracts
* Common enumerations
* Serialization contracts

The shared layer must remain independent of UI-specific implementation details.

Frontend components must not become the source of truth for backend contracts.

Backend implementation details must not leak into presentation-layer components.

---

# 2.2.1.9 — Analysis Architecture

The notebook requires advanced JavaScript analysis capabilities.

The long-term analysis system may include:

* AST analysis
* Syntax structure visualization
* Variable analysis
* Scope analysis
* Function analysis
* Loop analysis
* API analysis
* Program-flow analysis
* Data-flow analysis
* Runtime execution information
* Educational memory visualization

However, the AST parser and analysis implementation must not be selected solely because they are popular.

The analysis architecture must first define:

1. Required JavaScript syntax coverage
2. AST representation requirements
3. Source-location requirements
4. Transformation requirements
5. Static-analysis requirements
6. Runtime-analysis requirements
7. Visualization requirements
8. Performance requirements

The specific AST technology remains deferred.

---

# 2.2.1.10 — JavaScript Execution Architecture

JavaScript execution is a core backend concern.

The execution architecture must eventually support:

* Code execution
* Execution state
* Console/output capture
* Errors
* Execution timing
* Variable information
* Function information
* Loop information
* Program-flow information
* Data-flow information
* Instrumentation

Security and isolation are critical architectural requirements.

The execution engine must not be selected before the runtime boundary has been designed.

Therefore:

**Execution engine selection is deferred.**

# 2.2.1.13 — Responsive and Resizable UI Requirements

Responsive design is a first-class requirement of the new implementation.

The application must support:

### Computer

* Desktop monitors
* Laptop displays
* Wide layouts
* Multiple panels
* Resizable panels
* Notebook workspace
* Analysis workspace

### Tablet

* Touch-oriented interaction where appropriate
* Adaptive panel layouts
* Resizable or collapsible workspace regions
* Appropriate editor sizing
* Notebook usability at tablet dimensions

### Explicit Constraint

The project is computer- and tablet-oriented.

Mobile-phone optimization is not a primary target.

This requirement directly affects the frontend architecture and layout system.

---

# 2.2.1.14 — Resizable Panel Architecture

The new implementation must not repeat the previous project's limitation where panel resizing was not properly supported.

Resizable regions are planned for areas such as:

* Explorer
* Main notebook workspace
* Analysis
* Bottom/output panels

Panel behavior must be designed around:

* Minimum sizes
* Maximum sizes
* Drag interaction
* Keyboard accessibility where applicable
* Responsive behavior
* Layout persistence where appropriate
* Tablet interaction

The panel system must be reusable rather than implementing independent resizing logic inside each panel.

---

# 2.2.1.15 — Full-Stack Communication

The frontend and backend require an explicit communication boundary.

The communication architecture may eventually use:

* HTTP APIs
* WebSocket-based communication
* Other appropriate transport mechanisms

The exact transport must be selected according to execution, streaming-output, analysis, persistence, and application requirements.

It is therefore not finalized at this stage.

---

# 2.2.1.17 — Previous Implementation Boundary

The previous JavaScript Notebook implementation is not the dependency blueprint for the rebuild.

The previous implementation may be consulted for:

* Lessons learned
* Existing requirements
* UI/UX observations
* Problems
* Architectural observations

Its source code, dependency configuration, and implementation structure must not be copied into the new project.

---

# 2.2.1.18 — Repository Boundary

The project must remain a single Git repository.

Frontend, backend, and shared code are architectural areas within the same repository.

The project must not create:

```text
frontend/.git
backend/.git
shared/.git
```

or other nested repositories.

The root repository remains the single source-control boundary.

---

# 2.2.1.19 — Toolchain Installation Principle

Toolchain installation must follow the architecture.

The installation stage must not silently decide architectural questions that are intentionally deferred.

The installation process should establish only the foundation required to begin implementation safely.

---

# 2.2.1.20 — Stage Completion Criteria

Stage 2.2.1 is complete when:

* Full-stack project scope is explicitly defined.
* Frontend responsibilities are identified.
* Backend responsibilities are identified.
* Shared-layer responsibilities are identified.
* Core technologies are selected.
* Planned technologies are documented.
* Deferred technologies are documented.
* Responsive computer/tablet requirements are recorded.
* Resizable-panel requirements are recorded.
* Full-stack communication is identified as an architectural boundary.
* Dependency discipline is documented.
* Previous implementation reuse is explicitly prohibited.
* Toolchain installation can proceed without unresolved foundational ambiguity.
