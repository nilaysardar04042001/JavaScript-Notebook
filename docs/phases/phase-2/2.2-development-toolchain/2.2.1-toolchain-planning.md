# Stage 2.2.1 — Development Toolchain Planning

## Status

**Completed**

## Objective

Define the development toolchain before installing application dependencies.

The toolchain must support the JavaScript Notebook's long-term requirements:

- Notebook-style authoring
- Notes cells with text and images
- Markdown cells
- JavaScript coding cells
- JavaScript execution
- AST-based analysis
- Variable and scope analysis
- Function analysis
- Loop analysis
- API and network analysis
- Program execution visualization
- Data-flow visualization
- Educational memory-allocation visualization
- Data visualization
- Resizable workspace panels
- Responsive computer and tablet layouts
- Persistent notebook state
- Recovery and autosave
- Structured PDF export
- Automated testing
- Detailed project documentation

## 2.2.1.1 Toolchain Strategy

The project is not being rebuilt by copying the previous application's dependency setup.

The previous project may be used as reference material for lessons learned and requirements, but the new toolchain is selected independently.

The project will also avoid installing specialized dependencies before the architecture requires them.

## 2.2.1.2 Core Toolchain

### Node.js

Node.js is the development/runtime foundation.

The currently verified environment is:

- Node.js `v24.16.0`
- npm `11.13.0`

These versions are the current development environment observed during Stage 2.2.1.

### npm

npm is the package manager for the repository.

### TypeScript

TypeScript is selected as the primary implementation language.

Reasons include:

- Strong domain models
- Safer application contracts
- Better separation of domain and UI concerns
- Improved maintainability
- Better support for complex runtime and analysis data structures

### React

React is selected for the presentation layer.

React components must remain primarily responsible for presentation and interaction. Domain and application logic should not become tightly coupled to individual components.

### Vite

Vite is selected as the application development server and build tool.

It provides the required foundation for:

- Local development
- TypeScript/React integration
- Production builds
- Fast development feedback

## 2.2.1.3 Code Editing

### Monaco Editor

Monaco Editor is a planned dependency for coding cells.

The future editor integration is expected to support:

- JavaScript syntax highlighting
- TypeScript syntax highlighting where appropriate
- Code editing
- Cursor and selection behavior
- Error markers
- Future analysis integration

The exact integration is deferred until notebook cell and application architecture are established.

## 2.2.1.4 JavaScript Execution

JavaScript execution is a major architectural subsystem.

The application must not treat arbitrary notebook code execution as a simple `eval()` call inside the main UI context.

The future execution pipeline is expected to resemble:

```text
Code Cell
   |
   v
Execution Request
   |
   v
Execution Isolation
   |
   v
JavaScript Runtime
   |
   +-- Console Output
   +-- Return Value
   +-- Errors
   +-- Variables
   +-- Scope
   +-- Runtime Events
```

The exact execution mechanism will be decided during the runtime architecture stages.

## 2.2.1.5 AST Analysis

AST analysis is a core capability.

The analysis system will eventually need to identify structures such as:

- Variable declarations
- Functions
- Parameters
- Return statements
- Conditions
- Loops
- Expressions
- Calls
- Imports/exports where supported
- Other relevant JavaScript syntax

The exact parser/AST library is intentionally deferred until the analysis architecture is defined.

## 2.2.1.7 Responsive Design Constraint

Responsive behavior is a first-class requirement.

The target devices are:

1. Desktop computers
2. Laptops
3. Tablets

Mobile phones are not a primary target.

The workspace architecture must therefore support responsive panel layouts and panel resizing from the beginning rather than adding responsiveness as a late CSS correction.

A conceptual workspace may contain:

```text
+------------------------------------------------------+
| Header                                               |
+---------+-----------------------------+--------------+
|         |                             |              |
| Explorer|          Notebook            |   Analysis   |
|         |                             |              |
|         |                             |              |
+---------+-----------------------------+--------------+
|                 Bottom / Output                     |
+------------------------------------------------------+
```

The exact panel architecture will be designed in the UI foundation stages.

## 2.2.1.8 Visualization

Visualization is a major future subsystem.

It must eventually support:

- Data visualization
- AST visualization
- Program execution visualization
- Variable/scope visualization
- Loop visualization
- Function relationships
- Data-flow visualization
- Educational memory-allocation visualization

A visualization library is therefore not finalized at this stage.

The choice should follow the visualization requirements rather than being selected prematurely.

## 2.2.1.9 PDF Export

Structured PDF export is a planned core capability.

The final solution must support well-structured notebook exports containing appropriate combinations of:

- Notes
- Images
- Markdown
- Code
- Outputs
- Analysis information
- Visualizations

The PDF implementation will be selected during the export architecture stage.

## 2.2.1.10 Dependency Discipline

The project will avoid over-installation.

The dependency strategy is:

```text
Planning
   |
   v
Core development tools
   |
   v
Repository/source architecture
   |
   v
Feature architecture
   |
   v
Specialized dependencies
```

A dependency should be added when:

- The architecture requires it.
- Its responsibility is clear.
- The project benefits from using it instead of implementing the capability directly.
- Its maintenance and compatibility characteristics are acceptable.

## 2.2.1.11 Planned Development Scripts

The eventual package configuration is expected to provide commands similar to:

```text
npm run dev
npm run build
npm run preview

npm run typecheck
npm run lint
npm run format
npm run format:check

npm run test

npm run test:coverage
```

These scripts will be introduced progressively as their corresponding tooling is configured.

## 2.2.1.12 Toolchain Verification Principle

The project distinguishes:

```text
Installed
   !=
Configured
   !=
Verified
```

A tool is not considered part of the completed development foundation merely because its package is installed.

Each tool must be configured and verified through an appropriate command or test.
