# Stage 2.2.4.1 — Development Script & Command Strategy

## Status

**In Progress**

## Objective

Define the development command strategy for the JavaScript Notebook full-stack repository before modifying the root `package.json`.

The command architecture must support the long-term full-stack structure without introducing commands that depend on components that do not yet exist.

---

# 2.2.4.1.1 — Repository Command Boundary

The root `package.json` is the central developer command interface.

```text
                    package.json
                         │
             Root Command / Orchestration
                         │
          ┌──────────────┼──────────────┐
          │              │              │
          ▼              ▼              ▼
      frontend/       backend/       shared/
       React           Server        Common Code
```

The root package should coordinate the project but should not absorb implementation responsibilities belonging to individual architectural layers.

---

# 2.2.4.1.2 — Command Categories

The planned command system is divided into the following categories.

## Development

Commands for running development environments.

Examples:

```text
dev
dev:frontend
dev:backend
```

## Build

Commands for creating production artifacts.

Examples:

```text
build
build:frontend
build:backend
```

## Type Checking

Commands for validating TypeScript.

Examples:

```text
typecheck
typecheck:frontend
typecheck:backend
typecheck:shared
```

## Testing

Commands for automated testing.

Examples:

```text
test
test:frontend
test:backend
test:shared
```

These commands remain planned until the testing toolchain exists.

## Linting

Commands for static code analysis.

Examples:

```text
lint
lint:frontend
lint:backend
lint:shared
```

These remain planned until ESLint is configured.

## Formatting

Commands for code formatting.

Examples:

```text
format
format:check
```

These remain planned until Prettier is configured.

## Validation

A higher-level command may eventually coordinate the project's quality gates.

Example:

```text
validate
```

Its final contents will be determined after the relevant quality tools are implemented.

# 2.2.4.1.6 — Naming Convention

Command names will use lowercase kebab-free npm script identifiers.

Subsystem-specific commands use a colon separator.

Examples:

```text
dev
dev:frontend
dev:backend

build
build:frontend
build:backend

typecheck
typecheck:frontend
typecheck:backend
typecheck:shared
```

The naming system makes the command hierarchy immediately visible.

---

# 2.2.4.1.7 — Root Command Principle

Root commands should provide convenient project-level entry points.

For example:

```text
npm run typecheck
```

should eventually represent the project's complete TypeScript validation.

Subsystem commands provide focused execution:

```text
npm run typecheck:frontend
npm run typecheck:backend
npm run typecheck:shared
```

This provides both:

* Developer convenience
* Targeted troubleshooting

---

# 2.2.4.1.8 — Full-Stack Orchestration Principle

The long-term development command structure is:

```text
                 npm run dev
                      │
              Full-Stack Development
                      │
             ┌────────┴────────┐
             │                 │
             ▼                 ▼
      npm run dev:frontend   npm run dev:backend
             │                 │
             ▼                 ▼
          React/Vite          Node.js
```

The exact process orchestration mechanism will be selected only after the frontend and backend development commands exist.

No process-concurrency dependency should be introduced merely for planning purposes.

---

# 2.2.4.1.9 — Command Dependency Principle

Commands may depend on other commands when that relationship is meaningful.

Conceptually:

```text
typecheck
   │
   ├── typecheck:frontend
   ├── typecheck:backend
   └── typecheck:shared
```

and eventually:

```text
validate
   │
   ├── typecheck
   ├── lint
   └── test
```

The final dependency graph will be implemented only after the underlying commands have been established.

---

# 2.2.4.1.10 — No Placeholder Commands

The project must not contain scripts that appear functional but point to nonexistent files or tools.

For example, this should not be introduced prematurely:

```json
{
  "scripts": {
    "dev": "vite",
    "dev:backend": "node backend/src/index.js"
  }
}
```

if those entry points do not yet exist.

A command should either:

1. Work correctly, or
2. Not exist yet.

This keeps `package.json` trustworthy.

---

# 2.2.4.1.11 — Frontend Boundary

Frontend-specific commands belong to the frontend development environment.

Expected future responsibilities include:

```text
dev:frontend
build:frontend
typecheck:frontend
lint:frontend
test:frontend
```

The frontend command set must not directly implement backend behavior.

---

# 2.2.4.1.12 — Backend Boundary

Backend-specific commands belong to the backend development environment.

Expected future responsibilities include:

```text
dev:backend
build:backend
typecheck:backend
lint:backend
test:backend
```

The backend command set must not directly implement browser/UI behavior.

---

# 2.2.4.1.13 — Shared Boundary

Shared code is not treated as a separate application.

Its commands are primarily validation-oriented.

Expected future responsibilities include:

```text
typecheck:shared
lint:shared
test:shared
```

Shared code should remain reusable by both frontend and backend.

---

# 2.2.4.1.14 — Current Implementation Constraint

At the beginning of Stage 2.2.4.1:

```text
React/Vite application       ❌ Not configured
Backend application          ❌ Not configured
Shared source implementation ❌ Not configured
```

Therefore this stage is a **command strategy stage**, not an application implementation stage.

No frontend entry point, backend server, or shared application code will be created here.

# 2.2.4.1.15 — Relationship With 2.2.5

# 2.2.4.1.16 — Relationship With Backend Configuration

Backend-specific development commands will depend on the later backend configuration stage.

```text

        │
        ▼
Backend Entry Point
        │
        ▼
dev:backend
build:backend
```

This prevents the root command interface from becoming coupled to an undefined backend architecture.
