# Stage 2.2.4.2 — Root Development Commands

## Status

**Overall:** In Progress

## Parent Stage

**2.2.4 — Development Scripts & Project Commands**

## Objective

Establish the first root-level npm commands for the JavaScript Notebook full-stack repository.

# 2.2.4.2.2 — Root `package.json` Responsibility

The root `package.json` is responsible for exposing project-level commands.

It should provide a stable command interface for developers without becoming the implementation location for:

- Frontend application code
- Backend application code
- Shared application code
- Runtime configuration

The root package acts as the orchestration boundary.

---

The first commands introduced by this stage are TypeScript validation commands.

# 2.2.4.2.4 — Command Relationship

The intended command hierarchy is:

```text
typecheck
│
├── typecheck:frontend
├── typecheck:backend
└── typecheck:shared
```

The subsystem commands provide focused validation.

The root `typecheck` command provides project-level validation.

The exact npm implementation must ensure that failures from any required project configuration are correctly propagated.

# 2.2.4.2.5 — Frontend Typecheck

The frontend TypeScript configuration is:

```text
frontend/tsconfig.json
```

The command must operate against that explicit project configuration.

Conceptually:

```text
npm run typecheck:frontend
        │
        ▼
frontend/tsconfig.json
        │
        ▼
TypeScript validation
```

This prevents the root TypeScript configuration from accidentally becoming the frontend's only validation boundary.

# 2.2.4.2.8 — Empty Source Directories

At this stage, the frontend, backend, and shared directories contain TypeScript configuration but no application source implementation.

Therefore TypeScript's direct project checking may report an empty-input condition when invoked against a configuration whose `include` patterns do not currently match source files.

This is a known repository-state condition.

It must not be hidden by creating artificial application source files solely to satisfy the command.

The command behavior must be documented according to the actual state of the repository.

# 2.2.4.2.10 — No Placeholder Commands

The root `package.json` must not contain commands that reference nonexistent infrastructure.

For example, the following should not be introduced merely for planning purposes:

```json
{
  "scripts": {
    "dev": "vite",
    "dev:backend": "node backend/src/index.js"
  }
}
```

unless the corresponding application configuration and entry points actually exist.

The root command interface must remain truthful.

---

# 2.2.4.2.11 — Command Failure Propagation

Project-level commands must not silently ignore failures.

For example:

```text
typecheck
```

must eventually fail if one of its required TypeScript project checks fails.

This is important for:

- CI
- Git checkpoints
- Developer validation
- Future automated workflows

A successful exit status must represent a successful command.

---

# 2.2.4.2.12 — Command Naming

Commands follow the established naming convention:

```text
<operation>:<scope>
```

Examples:

```text
typecheck:frontend
typecheck:backend
typecheck:shared
```

The unqualified form represents the project-level operation:

```text
typecheck
```
