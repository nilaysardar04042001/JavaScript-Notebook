## Status

**Overall:** Implemented / Verified

---

# 1. Objective

Establish a technically correct module-resolution and build boundary between:

```text
frontend/
    │
    ▼
shared/
    ▲
    │
backend/
```

The objective is to ensure that the existing shared TypeScript source can be consumed safely by both frontend and backend during development and production builds.

This sub-stage exists because the first attempt to connect the backend directly to the shared TypeScript source exposed a module-resolution and build-boundary mismatch.

The issue has been resolved through **Candidate D — Root-Level Shared Build Boundary**, and the resulting development, build, and runtime behavior has been verified.

# 5. Backend Configuration

The backend configuration is:

```text
backend/tsconfig.json
```

It uses:

```text
module: NodeNext
moduleResolution: NodeNext
```

The backend therefore follows Node.js ESM module-resolution rules.

This creates a significant difference from the frontend configuration.

An extensionless relative import such as:

```ts
import { application } from "../../shared/src/application";
```

is not accepted under the backend's NodeNext resolution rules.

TypeScript reports that relative import paths need explicit file extensions.

---

# 6. `.ts` Extension Attempt

The following import was tested:

```ts
import { application } from "../../shared/src/application.ts";
```

TypeScript rejects this because importing a `.ts` extension requires:

```text
allowImportingTsExtensions
```

to be enabled.

The current project does not enable that option.

Therefore this approach is rejected.

We must not enable the option simply to bypass the module-resolution diagnostic.

---

# 7. `.js` Extension Suggestion

Under NodeNext, TypeScript suggests the runtime-compatible form:

```ts
import { application } from "../../shared/src/application.js";
```

This follows the general ESM principle that source TypeScript imports can reference the JavaScript filename that will exist at runtime after compilation.

However, this import alone does not solve the complete project architecture.

The production build boundary must also be considered.

---

# 8. Backend Build Configuration

The backend production build uses:

```text
backend/tsconfig.build.json
```

Current configuration:

```json
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "noEmit": false,
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/**/*.ts"],
  "exclude": ["dist"]
}
```

This establishes the following build boundary:

```text
backend/src/
       │
       ▼
backend/dist/
```

The build's `rootDir` is:

```text
./src
```

and the build includes:

```text
src/**/*.ts
```

The shared source is outside that boundary:

```text
shared/src/application.ts
```

Therefore the current backend production build does not establish a mechanism for emitting the shared source into the backend production output.

---

# 9. The Actual Architectural Problem

The problem is therefore not simply an import-extension problem.

There are two related boundaries:

```text
Development module resolution
            +
Production build resolution
```

The development question is:

```text
Can backend TypeScript resolve shared/src/application.ts?
```

The production question is:

```text
Will the compiled backend have the shared JavaScript module
available at the location referenced by its runtime import?
```

Both questions must have a valid answer.

---

# 11. Why a Direct Source Import Is Not Yet Accepted

A direct backend import such as:

```ts
import { application } from "../../shared/src/application.js";
```

may satisfy the NodeNext import-specifier rule, but the project must also demonstrate that the corresponding runtime module exists after backend compilation.

The current backend build:

```text
backend/tsconfig.build.json
```

does not include:

```text
shared/src/
```

in its source compilation boundary.

Therefore the `.js` import should not be treated as a complete solution until development and production behavior have both been verified.

# 13. Production Build Requirement


The runtime must not depend accidentally on an unbuilt TypeScript source file.

# 16. Candidate Architecture A — Direct Source Consumption

Conceptually:

```text
frontend ────────► shared/src
backend ─────────► shared/src
```

Advantages:

- Minimal structure
- No duplicated contracts
- Simple source organization

Problems:

- Frontend uses Bundler resolution.
- Backend uses NodeNext resolution.
- Backend requires runtime-compatible import specifiers.
- Backend production compilation currently excludes `shared/src`.
- Runtime output placement is therefore unresolved.

### Decision

**Not accepted as-is.**

It may become viable if the build boundary is deliberately redesigned and verified.

---

# 17. Candidate Architecture B — Shared Build Output

Conceptually:

```text
shared/src
    │
    ▼
shared/dist
    │
    ├────────► frontend/tooling
    │
    └────────► backend/runtime
```

Advantages:

- Explicit runtime JavaScript output
- Clear production dependency
- Clear separation between source and runtime artifacts

Considerations:

- Requires establishing a shared build process.
- Requires deciding whether shared should emit JavaScript and declarations.
- Requires deciding how frontend development consumes the source/build output.
- Adds additional tooling and build orchestration.

### Decision

**Requires explicit design before adoption.**

---

# 18. Candidate Architecture C — Independent Shared Package Boundary

Conceptually:

```text
shared/
├── package.json
├── src/
└── dist/
```

and:

```text
frontend ──► shared package
backend  ──► shared package
```

Advantages:

- Explicit package boundary
- Clear exports
- Clear runtime/build contract
- Strong long-term separation

Considerations:

- Introduces an additional package boundary.
- Requires package/build configuration.
- May be unnecessary for the current project size.
- Must be evaluated against the project's existing single-root-package architecture.

### Decision

**Not adopted at this sub-stage without further architectural justification.**

---

# 19. Candidate Architecture D — Root-Level Shared Build Boundary

Another possible approach is to establish shared compilation as part of the root project while maintaining:

```text
frontend/
backend/
shared/
```

as separate source areas.

Conceptually:

```text
                root build orchestration
                         │
             ┌───────────┼───────────┐
             ▼           ▼           ▼
         frontend     backend      shared
```

Advantages:

- Maintains the existing repository structure.
- Allows explicit build orchestration.
- Avoids copying shared source.
- Avoids immediately creating an independent npm package.

Considerations:

- Requires careful output-path design.
- Requires explicit module-resolution rules.
- Must prevent backend output from accidentally depending on source-only files.

### Decision

**Accepted and implemented: Candidate D — Root-Level Shared Build Boundary.**

The implementation was validated by building the shared module into `shared/dist`, consuming that generated module from the backend, compiling the backend successfully, and running the compiled backend against the `/health` endpoint.
