# 1. Objective

Define and verify the controlled consumption of the established shared contracts by the frontend and backend.

This sub-stage builds on the completed work from:

```text
2.2.7.1 — Shared Module Resolution & Build Boundary
2.2.7.2 — Shared Contract Implementation
```

The objective is to ensure that both application sides consume the shared contract from the correct boundary without duplicating its definition or introducing an invalid dependency direction, and to confirm that the current implementation remains aligned with that architectural boundary.


---

# 3. Consumption Principle

Consumption means that the frontend and backend use the shared contract as their authoritative definition.

It does not mean that frontend and backend should each create a local copy.

The intended model is:

```text
                 shared contract
                       │
              ┌────────┴────────┐
              ▼                 ▼
          frontend           backend
          consumer            consumer
```

Both consumers must obtain the contract from the established shared boundary appropriate to their build environment.

---

# 4. Frontend Consumption

The frontend uses:

```text
frontend/tsconfig.json
```

with:

```text
module: ESNext
moduleResolution: Bundler
```

The frontend may consume the shared contract directly from:

```text
shared/src/application.ts
```

because its Bundler-based environment resolves the source module correctly.

The frontend must not create a duplicate application contract.

The expected usage remains conceptually:

```ts
import { application } from "../../shared/src/application";
```

The exact import path should follow the repository's established source layout and TypeScript/Vite resolution behavior.

---

# 5. Backend Consumption

The backend uses:

```text
backend/tsconfig.json
```

with:

```text
module: NodeNext
moduleResolution: NodeNext
```

The backend production build must continue consuming the generated shared module:

```text
shared/dist/application.js
```

The established production import is:

```ts
import { application } from "../../shared/dist/application.js";
```

This keeps the backend build within:

```text
backend/src
```

and avoids pulling:

```text
shared/src/application.ts
```

into the backend `rootDir`.

The previously resolved `TS6059` problem must not return.

---

# 6. Development vs Production Consumption

The project has two relevant consumption contexts.

### Frontend development/build

```text
frontend
   │
   ▼
shared/src
```

through the frontend Bundler/Vite environment.

### Backend production build/runtime

```text
shared/src
   │
   │ shared build
   ▼
shared/dist
   │
   ▼
backend
```

The implementation must preserve the distinction between source-level frontend consumption and the established generated-module backend boundary.

---

# 7. Single Source of Truth

The source of truth remains:

```text
shared/src/application.ts
```

Consumers must not redefine:

```ts
type ApplicationState = ...
```

or:

```ts
const application = ...
```

locally.

The shared module owns the contract.

---

# 8. Dependency Direction

The allowed graph remains:

```text
frontend ──────┐
               ▼
             shared
               ▲
               │
backend ───────┘
```

The following are prohibited:

```text
shared → frontend
shared → backend
frontend → backend
backend → frontend
```

unless a later architecture decision explicitly establishes a different boundary.

---

# 9. Runtime Independence

The shared contract remains runtime-independent.

The frontend consumer may use the contract in React/Vite code.

The backend consumer may use the contract in Node.js code.

The shared implementation itself must not import:

```text
React
Vite
Node HTTP
Node filesystem
browser DOM
frontend components
backend services
```
