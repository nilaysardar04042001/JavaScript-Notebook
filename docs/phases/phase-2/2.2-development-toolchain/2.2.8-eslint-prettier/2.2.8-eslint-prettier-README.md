# 4. Scope

The final 2.2.8 formatting policy is an explicit active implementation/configuration scope.

The enforced formatting surface is limited to the project files that are actively maintained as source and repo configuration:

```text
Active source
├── frontend/src/**
├── backend/src/**
├── shared/src/**
└── scripts/**

Active configuration
├── tsconfig.json
├── frontend/tsconfig.json
├── frontend/vite.config.ts
├── backend/tsconfig.json
├── backend/tsconfig.build.json
├── shared/tsconfig.json
├── shared/tsconfig.build.json
├── eslint.config.mjs
└── .prettierrc.json
```

Historical documentation, generated output, and editor/tool artifacts are intentionally excluded from the formatting gate.

The configuration must not unintentionally lint or format:

```text
node_modules/
frontend/dist/
backend/dist/
shared/dist/
coverage/
historical documentation
```

unless an explicit later requirement says otherwise.

This rule is enforced both by a repository-level `.prettierignore` and by explicit file lists in the `format` and `format:check` scripts so the formatting gate cannot silently expand to unrelated files simply because the repository gains new Markdown or generated artifacts later.

---

# 5. ESLint Purpose

ESLint is responsible for identifying source-code problems and enforcing agreed code-quality rules.

It should focus on:

- TypeScript source
- React source
- General JavaScript/TypeScript correctness
- Unsafe or error-prone patterns where appropriate
- Consistent project conventions

ESLint should not become a replacement for TypeScript's compiler.

The existing TypeScript checks remain authoritative for TypeScript compilation.

---

# 6. Prettier Purpose

Prettier is responsible for deterministic source formatting.

Its purpose is to remove formatting debates and keep source files consistently formatted.

Prettier should control formatting concerns such as:

```text
Indentation
Quotes
Semicolons
Line wrapping
Trailing commas
Spacing
Bracket formatting
```

The final formatting rules should be established during implementation rather than invented in this planning document.

---

# 7. ESLint and Prettier Separation

The project should maintain a clear distinction:

```text
ESLint
  ↓
Code quality / correctness conventions

Prettier
  ↓
Code formatting
```

Formatting should not become a large collection of ESLint stylistic rules.

The configuration should minimize rule overlap between ESLint and Prettier.
