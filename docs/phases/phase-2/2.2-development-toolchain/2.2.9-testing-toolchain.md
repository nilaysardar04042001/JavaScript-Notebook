# 5. Required Testing Coverage

The testing foundation should eventually support the project's maturity model:

## 5.1 Shared Logic

Shared contracts and utility code should be testable in isolation.

This includes verifying:

- Type-safe shared contracts
- Pure utilities when present
- Boundary assumptions
- Contract compatibility

## 5.2 Backend Logic

The backend should be testable without requiring a browser or frontend runtime.

This includes validating:

- Request/response behavior
- Server startup behavior
- Runtime logic assumptions
- Integration boundaries

## 5.3 Frontend Logic

The frontend should be testable in a browser-like environment when appropriate.

This includes validating:

- React component rendering
- State-driven behavior
- User interaction logic
- Basic UI contract behavior

## 5.4 Integration Boundaries

The testing setup must remain mindful of the architectural boundaries already established:

```text
frontend ↔ shared
backend ↔ shared
frontend ↔ backend
```

The tests should verify the real integration behavior without coupling implementation details to unrelated layers.

---

# 6. Framework Selection

**Selected primary test runner: Vitest**

Vitest is selected as the repository's single primary test runner because the project already uses Vite, TypeScript, React, and ESM-oriented Node configuration. The testing foundation will use one runner across shared, backend, and frontend boundaries.

Frontend component testing will use Testing Library with a browser-like `jsdom` environment where appropriate.

`typescript-eslint` remains unrelated to the testing decision and remains deferred according to the 2.2.8 toolchain decision.

---

# 7. Framework Direction

The testing framework should be selected based on repository requirements and the project's existing toolchain decisions.

A lightweight, modern, developer-friendly framework is preferred.

The testing solution should support:

```text
Unit tests
Component or UI tests where appropriate
Node-based execution for shared/backend logic
Minimal configuration overhead
Compatibility with the current TypeScript toolchain
```

This stage should avoid introducing a complex multi-framework model simply because the project has multiple layers.

A single consistent test runner is preferred unless architecture requirements clearly justify more than one dedicated environment.

The selected testing toolchain must respect the constraints already established by the repository:
